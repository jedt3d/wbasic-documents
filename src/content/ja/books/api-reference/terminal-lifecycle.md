状態: **R6 の端末ライフサイクルと Windows の OSC52 読み取りは、検証した接続先の範囲で合格**

## 所有権とモード

`Tui.Run` は端末の使用権を取得し、機能を確認し、必要なモードに切り替え、処理ループを実行します。その後、端末を復元して使用権を解放します。同じ端末で入れ子の Run を行うと `Tui.AlreadyRunning` を報告します。先の後始末が完了すれば、次のセッションを開始できます。

全画面、行内表示、非対話の静的表示には、接続先に応じて対応します。非 TTY では制御シーケンスを出力せず、`NotInteractive` を報告します。復元時には入力と出力のモード、コードページまたは termios、画面、所有権を保ちます。コールバック、ワーカー、後始末で複数のエラーが生じた場合は、主たるエラーと `Suppressed` に記録した二次的なエラーを保持します。

## 出力停止時の方針

ホストが通常の出力を無期限に停止させた場合、承認済みの方針では入力を復元してから制限時間内にエラーを返します。保留中のパケットを正確に出力し、後始末を所定の順序で終えるまで、**端末の所有権を保持します**。その間は新しいセッションを開始できません。

例外的に Windows のホストが入力の復元自体を妨げる場合、入力と出力の後始末が残ったまま制限時間内にエラーを返すことがあります。すべての後始末が終わるまで所有権は保持されます。クリップボード出力が停止している間、OS の読み取りも止まる可能性があるため、ランタイムはネイティブ入力を OS の FIFO に残します。この間、イベントの配信は遅れることがあります。制限時間内に関数が戻っても、端末の完全な復元を意味しません。また、例外的な終了時にマウスイベントが再送される保証はありません。

Ctrl+C、一時停止と再開、接続の切断、端末を子プロセスへ引き継ぐ処理は、検証済みのプラットフォームでサポートされます。子プロセスの実行中、親はその画面を描き替えません。処理が戻ると画面全体を再描画します。

## クリップボード

- Windows では隔離された NativeLocal クリップボードのテストに合格しました。
- OSC52 の読み取りは、検証した macOS の接続先で合格しました。
- 固定した隔離環境の Microsoft ConPTY `1.24.260710001` では、実際の問い合わせに対する Unicode と空の応答、不正な応答と時間切れを区別するエラー、モードの復元を確認しました。古い標準のホストは正常な応答を転送せず、そこで WBasic は制限時間内に `Tui.ClipboardTimeout` を返し、モードを復元しました。
- Windows の証拠は **検証した接続先に限られます**。すべての端末での転送や、デスクトップのクリップボード管理方針は確立していません。
- 隔離された受け入れテストでは、通常のデスクトップのクリップボードを使っていません。

アプリはクリップボードイベントの `Text` と `Error` を、どちらも Null を許容する別の値として扱う必要があります。失敗と空のクリップボードを混同しないでください。

## 現在の対応環境

| プラットフォーム | 状態 |
|---|---|
| ネイティブ Windows 11 ARM64 | 記録された環境でコンパイラ、ランタイム、TUI、R7 の実例が合格 |
| ネイティブ macOS ARM64 | コンパイラ、ランタイム、TUI、R7 の実例が合格。iTerm2 の目視検査も合格 |
| Linux ARM64 | ネイティブの接続先での検証はまだありません |
| ネイティブ x86_64 | 受け入れ試験の全体は未合格です |
| SDK のない新しいホスト | 非公開の `0.0.2` ZIP は開発用ホストでの展開後検査に合格。独立した新規ホストでの受け入れは未完了 |

二つの ARM64 ホストでビルドに合格したことは、その範囲では強い証拠です。ただし、すべての OS と端末での合格を自動的に意味するものではありません。
